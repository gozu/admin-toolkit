# ADTK with Cobuild: what stays, what changes

The 64 capabilities now have individual **Existing / Headless-Cobuild** switches in Agents → Permissions. Existing remains the default. Selecting Cobuild does not grant execution permission or autonomous approval. The implementation was first deployed as 0.4.854 to akaos and TAMGLOBAL; comparisons continued on akaos through 0.4.859.

**Measured so far: 58/64 capabilities matched within their stated test scope.** Six remain unresolved. This is functional coverage, not an overall quality or speed score. Five formerly unresolved cases now pass: project deletion, continuous-activity stop (after streaming was licensed), installed-plugin uninstall, notebook-kernel shutdown, and store update. No native Headless replacement has been established for these executors.

The current Cobuild path is a bridge: **Cobuild requests the exact operation → ADTK executes it → Cobuild explains the actual result.** It uses the public Cobuild SDK service behind Headless. It does not launch the Headless MCP server or replace ADTK executors with native Headless tools. This preserves functionality, but it also means none of those executors can yet be removed.

The [CSV](adtk-cobuild-comparison.csv) and [interactive table](adtk-cobuild-comparison.html) contain one row for each of the 11 sensors and 53 actions. These are 64 capabilities, not 64 registered DSS tools: the actions sit behind the plan/execute entry points. Search, filter by verdict/type, sort any column, expand route details, or download the filtered rows. The same files are copied into the user’s Public folder. The table records measured outcomes; “not tested” is not a failure, and matching errors are not a pass.

**ADTK still provides the admin functionality.** That includes host selection and credentials; host macros; health checks, scoring and evidence collection; usage and dependency checks; plans and previews; capability gates; confirmations and token validation; backups; executors; audit/history; scenarios and scheduling; the agent interface; and the non-agent application. Headless can coordinate these functions through a bridge, but cannot replace access to the host, database, Kubernetes cluster or billing source merely by reasoning about them.

**The credit objective is only partly implemented.** The switched operations call Cobuild, and the earlier license/credit rejection on akaos no longer occurs. Under the supplied billing model, Cobuild usage credits pay for the Cobuild service independently of the customer’s BYO LLM token charges. The API responses used here did not expose billed credit totals, so this report does not invent per-tool credit consumption. The outer agent chat model has not been migrated. Therefore, “all in-scope agent inference uses Cobuild” is not yet achieved.

**The main observed tradeoff is latency.** Simple actions that took roughly 2–4 seconds on Existing have taken roughly 24–30 seconds through Cobuild in initial samples. The action path adds a request and result-explanation exchange during planning, then another during execution. Equal state changes do not make that delay disappear. Cache warming and measurement order also make some read timings unsuitable for speed comparisons. Functional parity, latency, explanation quality, audit persistence, reliability and credit consumption should be graded separately.

**The next architecture decision is the conversation boundary.** Moving the whole agent conversation to Cobuild would let it select operations and explain results within one ongoing conversation. That is a more useful destination than retaining the outer LLM and adding repeated Cobuild exchanges around every deterministic operation. Per-capability switches and ADTK’s execution controls should remain. A failed result explanation must never cause an already completed mutation to run again.

Headless’s project-oriented capabilities can add useful Flow, recipe, notebook and agent-definition work to ADTK investigations. ADTK’s diagnostic procedures and evidence requirements are plausible candidates to package as Headless skills. Approval enforcement, secret handling, filesystem safeguards and execution code must remain implemented controls; moving their prose into a skill does not replace those controls. ADTK’s application navigation, rendering, charting and session stores provide no direct value as Headless skills.

The three excluded standalone LLM features remain outside this migration: log AI analysis, failed code-environment advice, and report generation. The agent tools that inspect logs or administer code environments are still included among the 64.

**Validation limits:** a matched row certifies only its stated scope. `config_inspect` has been compared for project inventory, `toolkit_get` for the version endpoint, and `k8s_health` for an empty cluster inventory. Docker coverage is image pruning, with all pre-existing image IDs preserved; builder-cache pruning remains untested. Database maintenance used one disposable 10-row table and a temporarily configured DB Health credential, which was restored afterward. Those are not tests of every branch. The initial local runner could not write audit rows. A later in-DSS test verified the project-variable change, audit ID and settings-history record on both paths after supplying the test runtime's missing database driver. Live comparisons used akaos admin access; non-admin role parity remains untested. Raw customer diagnostics, credentials, confirmation tokens and model transcripts are not included in these public artifacts.

**The remaining six are explicit.** Cluster start/stop still need the requested stable deployment window. The finished-pod test now waits for asynchronous deletion, but requires another live cluster to validate it. Image deletion needs an approved older image because the server rejects fresh images; plugin deployment needs an authorized second host; Python execution is waiting for the exact-code approval requested for `print(6 * 7)` on each path.

**What the retries fixed:** installed-plugin uninstall/update now archive source through an admin-only macro on the selected host. The old download API only exports development plugins ([DSS API reference](https://doc.dataiku.com/dss/api/latest/rest/)). Backup failure still prevents mutation. Live uninstall comparisons checked deletion, binary file preservation, and successful reinstallation from each backup before removing the restored fixture. The store-update action now uses the configured long-operation timeout; mutation timeouts explicitly report an unknown outcome, with no automatic execution retry. The notebook fixture now establishes the Jupyter session and its CSRF token correctly. Tests of streaming and notebooks independently verify that running activity stops and notebook files survive.

The first clean project-delete comparison took 1.358 seconds on Existing and 15.900 on Cobuild; continuous-activity stop took 2.796 and 21.672; plugin uninstall took 2.065 and 20.536; notebook shutdown took 1.195 and 15.646. Store update took 75.621 and 89.184 seconds, including DSS's shared plugin-image rebuild. It replaced an owned empty 0.0.0 placeholder with the store's 0.1.0 source and backed up the placeholder; this does not certify migration of an in-use plugin. These remain single successful samples, not latency guarantees. Backend interruptions and fixture-setup failures do not constitute three meaningful Cobuild improvement attempts.

The comparison runners cap candidate attempts at three and reset or reconcile disposable fixtures before another execution. Fixture setup errors are tracked separately from Cobuild failures. The Kubernetes test used exactly one ready `t3.small` node. The node, EKS control plane, node-group stack and control-plane stack were subsequently verified deleted, and the DSS attachment was removed. Test projects, users, channels, connections, variables and disposable configurations were checked for leftovers; test settings were restored. The dedicated empty `ATKCOBUILDTEST` project remains for the earlier Cobuild conversation traces.

Retry validation on 14 September: 832 backend tests and 17 subtests passed, along with frontend typecheck, packaged build and contract checks. The Public table was checked in Chromium for 64 rows, 58 matched rows, filtering, route details and CSV export. Release 0.4.859 is deployed to akaos and TAMGLOBAL. The maintenance audit has no errors; its existing unreferenced overview screenshot warning remains.

Retry cleanup is complete: the disposable projects, notebook sessions, streaming activity, plugin fixtures and macro environment were removed; touched capability gates were restored. No new cluster was provisioned during these retries. After removing the fixtures, DSS successfully rebuilt its shared plugin container image from the remaining installed plugins. Historical image layers/cache were not pruned.
