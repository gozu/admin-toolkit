Admin Toolkit · agent tools and skills

Headless or Cobuild or Neither

For every tool, read, action and skill the Admin Toolkit agents carry today: can Dataiku Headless do it, can Cobuild do it as a fallback, or must it stay in the Toolkit, and why.

Checked 14 September 2026 against Headless 0.6.0 (commit 9d7f6cc, 128 tools), Toolkit 0.4.830 source, and live runs on TAMGLOBAL as the non-admin user kaosdex in project KAOSHEADLESS.

The short answer. Headless covers the plain DSS inventory work the Toolkit agents do: projects, connections, code envs, plugins, users, LLM connections, scenarios, webapps, jobs and datasets, plus fourteen of the fifty-three admin actions. Cobuild adds in-project building and deletion with its own confirmation flow. Everything that makes the Toolkit an admin product falls outside both: host filesystem and logs, Kubernetes and PostgreSQL health, cost and adoption analytics from audit logs, cluster and connection writes, fleet routing, and the plan-confirm-execute safety layer.

  • Headless can take over 10 of 19 config domains, 14 of 53 actions, and the read-only halves of 2 curated reads.
  • Cobuild is a real fallback for 5 actions that change project assets, and for narrative synthesis if the Toolkit hands it evidence.
  • Neither can do all 11 sensors as designed, 19 of 21 curated reads, 8 config domains and 34 actions. The reasons group into five buckets, listed below.
  • One thing prior write-ups missed: Cobuild is a public REST API in the Dataiku client since 14.7.2. The Toolkit backend can talk to it directly, without the Headless MCP wrapper.

The three options, in plain words

These are three different places code runs, with three different identities. That is what decides most of the dispositions below, more than any tool list.

Headless preferred

An MCP server that runs on the operator's laptop inside Codex or Claude Code. It wraps the Dataiku public API with 128 tools and ships two skills plus 55 reference guides.

Runs
Locally, next to the harness
Identity
The operator's own API key. Four tool groups refuse non-admins: users, groups, licensing, general settings.
Reaches
One configured DSS instance at a time. Public API only. No host filesystem, shell or logs.
Reasoning
The harness model. Not a Dataiku AI credit.

Cobuild fallback

Dataiku's server-side building agent, scoped to one project. Headless drives it with six tools, but the same conversation API is in the public client.

Runs
Inside DSS, on the instance
Identity
The calling user. Project permissions apply.
Reaches
Project assets: flows, recipes, models, dashboards, agents, scenarios, wikis. Not instance administration.
Reasoning
Metered Dataiku AI Services usage. Needs DSS 14.7 or newer.

Neither stays in Toolkit

The Toolkit's plugin backend, running in DSS with an admin key, with macros for anything that touches the host.

Runs
Inside DSS, plus macros on the host
Identity
Admin key, or the managed-host key for remote instances
Reaches
Admin API, DIP_HOME, backend.log, kubectl, the runtime PostgreSQL, container registries, a whole fleet
Reasoning
LLM Mesh today. Could become Cobuild for synthesis.

Why "neither", in five buckets

Every "neither" row below cites one of these. If a bucket goes away upstream, its rows flip.

  1. Host access. Reads or writes the DSS host itself: DIP_HOME tree, backend.log, tmp and export folders, Docker, process table. Headless is public-API only; Cobuild is project-only.
  2. Admin API not wrapped. The public API has it, Headless has no tool for it: clusters, API keys, connection writes, global variables, general settings writes, notebook kernels, webapp backends, continuous activities, scenario abort, project delete/export/owner, messaging.
  3. Derived analytics. Needs audit logs or a cross-instance scan plus Toolkit rules: health score and sanity, CRU cost, adoption and churn, LLM audit, app-instance attribution, compute placement.
  4. Infrastructure beyond DSS. kubectl against attached clusters, the runtime PostgreSQL, container registries.
  5. Toolkit-internal. Only meaningful inside the Toolkit: capability manifest, action audit timeline, settings snapshot, version, agent-authored Python, Toolkit scenario writer.

What overlaps, and what to do about it

The overlap is the ten inventory domains and fourteen actions above. Two ways to remove the duplication, and they are not equal:

  • Give the Toolkit agent Headless tools. Headless is a laptop-side MCP server. The Toolkit agent runs inside DSS, so the only way to reuse the code is to import its tool functions into the plugin backend and call them with the admin client. Works for reads. For writes it would strip out the plan step, confirm token, backups and audit that the Toolkit adds.
  • Give Headless the Toolkit's knowledge. Port the playbooks as reference guides so an operator in Codex gets the same judgment for the domains Headless already covers. This is the cheaper move and the one that reaches operators who never install the Toolkit.

Recommendation: do the second for the ten covered domains and the green and amber actions. Keep the Toolkit executors for every red action even where Headless has a raw tool, because the upstream tools have no dry run, no backup and no self-lockout guard.

In Headless, not in the Toolkit agents, and worth adopting

The Toolkit agent sees the instance from the top down. Headless sees inside projects. These upstream reads would answer scoping questions the agent currently cannot, and they are all public-API reads the plugin backend can call today.

Toolkit skills worth porting to Headless

Port as reference guides

  • Action safety pattern. Plan, show the target shape, drift-check the current value, then execute. Headless admin writes have none of this. It ports as guide text plus a request for a dry-run flag upstream.
  • Remediation map and severity playbook. Which finding points to which action, and what counts as critical. Domain knowledge, not code.
  • Code-env hygiene. Deprecated Python detection, unused-env rules, consolidation order. Headless has the inventory, not the judgment.
  • Plugin drift. Comparing versions across instances is a two-profile workflow Headless can already do with switch_instance.
  • Connection audit rules. Fast-write, details readability, filesystem root findings, computed from get_connection_info.
  • Scoping prompts for projects and envs. The catalog entries for project landscape, dominant projects, env estate and env drift run on domains Headless covers.

Not useful to Headless

  • Repository maintenance skill. Release and docs upkeep for this codebase.
  • Frontend contracts, stores, module registry. React internals.
  • Fleet prompts. Sweep, compare, quiet, outage. Headless has no fleet concept.
  • Host, Kubernetes, database and Docker prompts. Buckets 1 and 4. The guide would describe tools that do not exist.
  • Cost and adoption prompts. Bucket 3. Audit-log analytics.
  • Safety drills. They test the confirm-token machinery, which Headless does not have.
  • System prompts and rubrics as-is. They reference Toolkit sensor names and gates. Only the domain knowledge inside them ports.

What was verified, and how

  • Headless tool inventory read from source at commit 9d7f6cc, cloned fresh today. The 128-tool split of 93 read, 21 write, 6 Cobuild, 4 execute, 3 profile, 1 test is upstream's own count in docs/capabilities.md.
  • Admin gating confirmed by grep: require_admin() is called only in users, groups, licensing and general settings.
  • Toolkit catalogs imported from tools_impl, domain_registry, read_registry and actions: 11 sensors, 19 domains, 21 reads, 53 actions, 39 pages.
  • Live on TAMGLOBAL as kaosdex (DSS 14.7.3, evidence file docs/headless-integration-evidence.json): seven reads succeeded, licensing refused with "you are not admin", a Cobuild conversation created an agent tool and a native agent, and Cobuild reported it cannot invoke plugin tools, macros, or read users or host state.
  • Cobuild public API confirmed in dataiku-api-client 14.7.2: DSSProject.new_cobuild_conversation, send_message, answer_confirmation, answer_question.
  • Not verified: the four Cobuild-fallback actions marked "not live-tested", and any Cobuild usage debit. Earlier attempts on akaos were credit-blocked.

Recommended sequence

  1. Port the six guide-worthy playbooks to Headless reference format and open them upstream. No Toolkit code changes, immediate reach.
  2. Adopt the flow-graph, dataset-profile, plugin-usage and job-wait reads into the Toolkit agent as new sensors, calling the public API through the existing admin client.
  3. Pilot Cobuild as the synthesis step for the scheduled triage sweep, calling it through the public client from the plugin backend. Measure a usage delta on a customer-scoped identity before claiming anything about credits.
  4. Ask upstream for four things that would flip rows here: a dry-run flag on admin writes, cluster and connection write tools, scenario abort, and a way for Cobuild to call registered plugin tools.
